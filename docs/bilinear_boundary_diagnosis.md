# 位相関数ソルバの共有境界エラー：診断と修正の根拠

調査日：2026-10-12．診断対象の基準コミット：
`a473f614723a6ac4ebc68dcee18e1856f9208314`（`fix/solver-crash`）．

**添付の失敗一覧は 377 条件であり，全件が `cdf_input_boundary_pending` に分類されている．
そのうち先頭条件に対応する局所的な CPU 再構成では，問い合わせ方向が出射パッチの
共有頂点に厳密に一致し，同じ光路が隣接する 4 パッチから報告される状況を再現した．**
修正では，正則なパッチ間の共有境界について一意の担当パッチを決め，この重複を処理する．

修正版の CPU 検証では，この局所的な 4 件の報告が 1 件に統合され，光学評価と焦点位相評価が
正常に完了した．**実 GPU 上の全 377 条件や，この 1 条件の完全な CDF の再計算は，
この調査環境では実施していない．** 全件の解消を確認する手順は
[失敗条件だけを再計算する手順](retry_boundary_failures.md)に記載する．

## 1. 添付された失敗一覧から確認できること

調査に使用した `failures(3).json` は，個別ログの内容を含まない集計ファイルである．

| 項目 | 確認結果 |
| --- | --- |
| 全条件数 | 27,300 |
| 成功済み | 26,923 |
| 失敗 | **377**（`count`，`jobs` の要素数，重複を除いたジョブ名数が一致） |
| 未試行 | 0（報告された実行結果による） |
| 失敗率 | 約 1.38095% |
| 失敗カテゴリ | 全件 `cdf_input_boundary_pending` |
| `attempt_count=2` | 250 件 |
| `attempt_count=1` | 127 件 |
| 失敗した入射角 | 199 種類，−89.7°～89.1° |
| 失敗した波長 | 90 種類，380～830 nm |

依頼文中の「337 件」は，集計ファイルと `27300 - 26923 = 377` に一致しない．
再計算対象は，この一覧の時点では 377 件である．各条件は
`inclination_degrees = -89.7 + 0.6 * incident_index`，
`wavelength_nm = 380 + 5 * wavelength_index` に一致している．

全件の生成世代の署名は次のとおりである．

```text
cf38c5c0833ac82dc3f40e4aca2924a1d4a2e04e18fb9d7db0bff2e8d750e660
```

試行回数 2 の 250 件は，ソートされた一覧の先頭 `i0000_w0081` から
`i0204_w0070` までで，タイムスタンプ付きのログを参照する．残りの 127 件は
`i0206_w0056` から `i0298_w0059` までで，試行回数 1 の通常のログ名になっている．
これは一部の条件まで再試行した状態と整合するが，再試行が止まった理由は集計だけでは分からない．

カテゴリの判定は
[`inspect_job_failure()`](../tools/generate_phase_dataset.py)にある．
`CDF_accumulation_started=0` を含む認識可能な CDF 入力拒否のログで，
`optical flags=64` と正の `boundary_hits` が検出された場合に，このカテゴリが付く．
したがって，この一覧は共有境界に関する未解決の光学入力を調べる根拠になる．
**カテゴリの一致だけでは，全 377 件が同じ幾何学的状況にあることまでは証明できない．**

集計には，各条件の `failure_record` と `log` の相対パスはあるが，個別の診断値や
GPU 上のパッチ頂点は含まれない．先頭条件の追加資料に相当するパスは次である．

```text
failures/i0000_w0081.json
logs/i0000_w0081.1791716822543202800.log
```

## 2. CPU で再構成した具体的な共有頂点

リポジトリにあるログ形式のテストデータ
[`CDF_REJECTION`](../tests/test_generate_phase_dataset.py)には，問い合わせ方向
`1687286`，最初の問題パッチ `32956688`，境界ヒット 4 件という診断が保存されている．
このログ形式のテストデータ自体は数値シミュレーションではない．
そこで，先頭の失敗条件と既存設定に合わせ，以下の条件で共有コードを実際に CPU 実行した．

| 項目 | CPU 再構成の設定 |
| --- | --- |
| 雨滴半径 | 1.0 mm |
| 形状 | 既存の非球形雨滴モデル |
| 入射角 | −89.7° |
| 波長 | 785 nm |
| 水の状態 | 20 °C，101325 Pa |
| 内部屈折率の FP32 値 | 1.3288713693618774 |
| 入射頂点グリッド | 3001 × 3001 |
| 問い合わせグリッド | 1800 × 3600 |
| 問い合わせ方向 ID | 1687286 |
| 問い合わせの角度 | θ = 46.85°，φ = 68.65° |

使用したのは，[物性値の評価](../src/water_refractive_index.cpp)，
[雨滴の交差判定](../include/rainbow/raindrop_intersection.hpp)，
[`RaindropPathTracer`](../include/rainbow/raindrop_paths.hpp)，
[`QueryDirectionGrid`](../include/rainbow/query_direction_grid.hpp)である．
必要な格子頂点と周辺パッチだけを再構成し，全 900 万余りの入射頂点を追跡したわけではない．

問い合わせ方向の FP32 成分は次のとおりだった．

```text
(0.6830700635910034, 0.6803435087203980, 0.2656087279319763)
```

ビット表現は `(0x3f2eddae, 0x3f2e2afe, 0x3e87fdde)` であり，
**TRRT の出射頂点，入射格子座標 `(1689, 1986)`，グローバル頂点 ID `32979678`
の方向と 3 成分すべてが一致した．** 以下の 4 パッチがこの頂点を共有する．

| パッチ ID | 入射セル座標 `(x,y)` | 交差の局所座標 `(u,v)` | パッチ分類 |
| --- | --- | --- | --- |
| 32956688 | (1688, 1985) | (1, 1) | `RegularPositive` |
| 32956689 | (1689, 1985) | (0, 1) | `RegularPositive` |
| 32959688 | (1688, 1986) | (1, 0) | `RegularPositive` |
| 32959689 | (1689, 1986) | (0, 0) | `RegularPositive` |

基準コミットの交差判定では，全件が `BilinearBoundary | BilinearUsedFp64`，
再構成残差 0 となった．長倍精度の独立した代数計算でも同じ端点解を得た．
さらに，FP32 の入力を正確な有理数として扱う Python `Fraction` の計算で，
共有頂点に接する辺と問い合わせ方向の三重積が厳密に 0 であることを確認した．
このゼロ判定は，`long double` の精度や，浮動小数点のしきい値には依存しない．

この事例では，単に境界に近い内部点を境界と誤判定しているのではない．
**格納されたパッチそのものに対して，真の共有頂点への問い合わせが発生している．**
元の光学評価は境界の担当パッチを決定できず，4 件とも未解決として扱っていた．

再構成した 9 個の一意な頂点方向のビット列と 4 パッチの接続関係は，
[`test_cpu_reconstructed_exact_corner()`](../tests/bilinear_boundary_ownership_cases.hpp)
に保存した．将来のトレーサの丸め方が変わっても，同じ問い合わせ問題を検査できる．
ただし，これは **CPU 再構成の固定データであり，実行時の GPU バッファの採取データではない**．
個別ログとの完全な照合や，他の 376 条件への一般化には追加の実行結果が必要である．

## 3. 共有境界の担当パッチを一意にする

論文 *Physically-Based Simulation of Rainbows* の第 4 節と第 4.1.1 節は，
隣接する入射レイから出射パッチを構成し，問い合わせ方向で補間した複素電場を合成する
手順を述べている［1］．同じ入射格子の辺・頂点を複数の閉じたパッチが共有した場合の
担当パッチの選択規約は，これらの節では指定されていない．

今回の実装では，次の離散化規約を明示的に追加する．

1. 格納された FP32 の頂点と問い合わせ方向から，正則パッチの内側・外側・境界上を判定する．
   境界付近では元の入力の辺の三重積の符号を厳密に評価し，`u` や `v` が保存時に
   0 または 1 に丸められたことだけで共有境界を確定しない．
2. 共有辺は，**入射側のグローバル頂点 ID の組**で識別する．共有頂点は 1 個の
   グローバル頂点 ID で識別する．出射方向の近さによるグループ化は行わない．
3. 同じ向きの正則パッチから同じ入射側の共有境界が報告された場合，
   **`patch_id` が最小の 1 パッチを担当とする**．BVH の訪問順序や compact index に依存させない．
4. 保持した境界ヒットに所有権が解決したことを記録し，そのパッチの既存の補間・位相・
   面積スケーリングを用いて評価する．重複した隣接パッチの寄与を加算したり平均したりしない．

正則性は別の判定で確認し，厳密な辺の符号だけを使って折り返したパッチまで正則とみなすことはない．
関連する実装は，[境界の符号判定](../include/rainbow/bilinear_patch_boundary.hpp)，
[双線形パッチの交差判定](../include/rainbow/bilinear_patch_intersection.hpp)，
[ヒットの収集と所有権の解決](../include/rainbow/patch_query_data.hpp)，
[光学評価](../include/rainbow/patch_optical_evaluator.hpp)である．

グローバル頂点 ID は光路の種類ごとに分かれているため，R，TT，TRT，TRRT などの
**異なる光路が同じ出射方向に届く場合は，それぞれの寄与を保持する**．同じ光路の種類でも，
入射側では離れている領域が出射側で重なっただけなら，別の寄与として保持する．
これは，論文の第 4.1.1 節，図 10，式 (4) が扱う異なる波面間の干渉と区別する必要がある［1］．

真の折り返しや特異な解，逆向きのパッチが接する状況，必要な境界情報を持たない隣接報告は，
今回の規約では解決済みにしない．同じ共有境界に未対応の報告が残る場合は，正則な報告だけを
取り出して部分的に完了させることも避ける．また，NaN，不正なパラメータや root index などは
重複除去の前に検査し，担当外のパッチを捨てる際に数値エラーまで消さない．

## 4. 境界で有限のパッチ近似値が一致するとは限らない

論文では，入射セル面積と出射立体角の比を強度に対応させ，複素電場の振幅にはその平方根を
乗じる［1，第 4 節・第 4.1.1 節］．実装もこの面積スケーリングを用いている．
したがって，共有頂点の電場と光路長が共通でも，有限解像度の隣接パッチでは
`incident_area / abs(signed_solid_angle)` が完全には一致しない．

上記の CPU 再構成では，全パッチの入射面積は `4.9842287808132824e-7` であり，
出射立体角と比率は次のとおりだった．

| パッチ ID | 出射立体角 Ω | 入射面積 / Ω |
| --- | --- | --- |
| **32956688：選択される担当** | 2.6858863293455215e-6 | 0.18557109905793390 |
| 32956689 | 2.6864063329412602e-6 | 0.18553517834199751 |
| 32959688 | 2.6883926693699323e-6 | 0.18539809446740591 |
| 32959689 | 2.6884556518780300e-6 | 0.18539375114227874 |

比率の最大値と最小値の差は，最小値に対して約 **0.0956601%**，
選択された担当の値に対して約 **0.0955687%** である．各パッチを独立に評価した診断では，
全件の光学フラグと焦点位相フラグが 0，TRRT の焦点位相は 1 quarter turn だった．
共有頂点での位相・偏光は一致し，振幅は上記の面積比の平方根に応じて異なった．

この結果から，担当の選択は有限のパッチ近似における境界値の規約であり，
4 パッチがまったく同じ数値を返すから重複を消してよい，という説明は正確ではない．
連続な方向空間で境界が測度 0 であることも，有限の角度グリッド上で境界を直接評価した値や
そのセルに割り当てる質量が無関係になることを意味しない．

**約 0.0956% は，この 4 パッチの局所的な面積比の差であり，位相関数全体や画像の誤差ではない．**
他の光路との干渉もあるため，この数値を最終的な放射強度の相対誤差へ直接読み替えることはできない．
解像度の収束や論文・参照解との一致度は，別の実験で評価する必要がある．

## 5. 修正後に確認できた局所的な光学結果

同じ条件を CPU の共有コードで再追跡し，今回のヒット収集と光学・焦点位相評価へ渡した結果は
次のとおりだった．ここで評価したのは上記共有頂点周辺の **TRRT の寄与だけ**である．

| 項目 | 修正後の局所結果 |
| --- | --- |
| 境界の生の報告数 | 4 |
| 保持したヒット数 | 1 |
| 担当パッチ | 32956688 |
| 除去した共有境界の重複報告 | 3 |
| Query flags | 544 = `PatchQueryFp64Used` + `PatchQueryBoundaryResolved` |
| Optical flags | 0 |
| `known_hits_complete()` | `true` |
| 評価済み / 拒否ヒット | 1 / 0 |
| TRRT の incoherent s 強度 | 4.6585277292425995e-5 |
| TRRT の incoherent p 強度 | 2.4859809859883789e-5 |
| Focal flags / `valid()` | 0 / `true` |
| Focal corrected hits / TRRT family hits | 1 / 1 |
| TRRT の focal s 強度 | 4.6585275572178489e-5 |
| TRRT の focal p 強度 | 2.4859808941889339e-5 |

修正後の incoherent 強度は，担当パッチを独立に評価した診断値と一致した．
4 パッチ分の電場を加算して強度を増やしたり，未解決の寄与をゼロで置換したりせず，
選択した 1 パッチの既存の光学計算が通ることを確認した．

`known_hits_complete()` は，渡されたヒット集合の評価が完了したことを表す．
この局所実行では R や TT の別の光路，6,480,000 方向全体の評価，回折処理，CDF 構築を
実施していないため，このフラグを条件全体の完成や物理的な正確さの証明に使ってはいけない．

## 6. 回帰検証

今回の変更を含む共有 CPU コードについて，C++20，`-O2 -fno-fast-math -ffp-contract=off`
と警告を有効にしたビルドで，以下の検証に合格した．GPU の検証結果とは分けて扱う．

| 検証 | 結果・範囲 | ソース |
| --- | --- | --- |
| 双線形交差・ヒット収集 | 12,000 件の独立参照比較，既存の境界回帰，新規の所有権回帰に合格 | [CPU query test](../tests/test_patch_query_cpu.cpp)，[所有権の回帰](../tests/bilinear_boundary_ownership_cases.hpp) |
| 厳密な境界符号 | C++ の解析的な事例と，独立した整数演算の参照 11,010 件に合格 | [C++ test](../tests/test_bilinear_patch_boundary_cpu.cpp)，[整数参照](../tests/check_bilinear_boundary_exact.py) |
| 光学評価 | 533 件に合格 | [CPU optics test](../tests/test_patch_optics_cpu.cpp) |
| 焦点位相・波動処理 | 2,274 checks に合格 | [CPU wave test](../tests/test_wave_optics_cpu.cpp) |
| 折り返しパッチ | 270 checks に合格 | [CPU folded test](../tests/test_folded_patches_cpu.cpp) |
| データセット再開処理 | 115 tests を実行，114 合格，Windows の共有ロックを要する 1 件をスキップ | [batch tests](../tests/test_generate_phase_dataset.py)，[generation tests](../tests/test_generate_phase_dataset_generations.py)，[commit tests](../tests/test_generate_phase_dataset_commit.py) |

新規の所有権回帰には，共有辺・共有頂点の一意化，全 24 通りの訪問順序，compact index の
並べ替え，単独の有効な境界パッチ，異なる光路の保持，FP32 保存時に端点に丸められる内部解，
折り返しパッチの 2 個の解の保持を含む．正則・未分類・特異・逆向きの境界が混在するケースや，
担当外となる報告に NaN などが含まれる 10 種類のケースも検査する．

光学計算へ接続する人工的な事例では，無偏光入力の 2 応答列について，期待される電場と
強度を独立な簡単な算術で指定した．これにより，4 個の隣接パッチを別の光路として
加算・平均・再スケーリングしてしまう変更を検出する．実際の CPU 再構成については，
前節の局所実行と固定したビット列による回帰を別に実施した．

バッチの Python テストではソルバ子プロセスを模擬しており，光学的な精度や GPU での
失敗の解消を検証しているわけではない．この環境では CUDA／OptiX を実行できず，
完全な CMake 構成，`nvcc` ビルド，GPU の回帰検証も未実施である．

## 7. 実データでの完了判定

成功済み 26,923 条件を保持した再試行，旧バイナリの保存，世代登録，終了コードの解釈は
[再計算手順](retry_boundary_failures.md)にまとめた．1 件の試行が成功しても，残りに
失敗があればデータセット全体の終了コードは 2 のままになる．

全件完了を主張する条件は，実際の再試行後に `completed=27300`，`failed=0`，
`unattempted=0`，`complete=true`，`failures.json` の `count=0` を確認することである．
今回の CPU 再構成から「全 377 条件が解消した」とは結論しない．

失敗が残った場合は，更新された集計と該当する個別失敗レコード・ログを調べる．
必要に応じ，診断ビルドの `--patch-failure-report` で，CDF 構築に使った同じ GPU 結果から
パッチ情報を採取できるようにした．実装は
[`rainbow_generate`](../apps/generate_phase.cpp)と
[パッチ失敗レポートの採取](../src/patch_failure_capture.cpp)にある．
これは診断を追加する機能であり，未解決の入力を成功扱いに変更する機能ではない．
